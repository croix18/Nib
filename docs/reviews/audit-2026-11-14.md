# Audit of Nib 1.6.6, 14 November 2026

Croix asked for "a high level audit and hardening on the entire nib project". This is what was checked and how, what
was found, what 1.6.7 fixed, and what was left and why. The fixes themselves are described where the code is described
(`docs/HANDOFF.md`, Hardening (1.6.7)); every one is pinned by `test/hardening_check.js` or
`test/hardening_browser.js`.

## The short of it

The code was in good shape where it meets the outside: saved work, opened files and settings were already checked
field by field, and nothing in the repository or its history should not be there. What was weak was what happens when
something inside goes wrong or grows without limit. One piece of writing that could not be read stopped all reading on
its page. A very long stroke froze the Board when the pen lifted. A letter written far outside its box could hang the
Replicator for good. And the tests did not notice half of a sample of planted bugs, nearly all of them limits and
guard rails.

## What 1.6.7 fixed

1. **Reading survives a piece of writing that cannot be read.** Before: an exception while reading one cluster escaped
   from a timer, no result was announced, and every later read threw again at the same place. Now that cluster stays
   ink, the rest is read and answered, and it is said once (`console.warn`, a `nib:fault` event, `pad.faults`). The
   same goes for a view or an answer that cannot be worked out, an element that cannot be drawn, and the scribble and
   shape checks at pen lift.
2. **A long stroke no longer freezes the Board.** The scribble detector ran on every lifted stroke with work that grew
   with the stroke. It now has bounds, and under them does the same work faster with the same answers (all 38,280
   detections and 7,759 erase decisions of `scribble_check` compared with the 1.6.6 functions: no difference).

   | One stroke | 1.6.6 | 1.6.6, CPU 4x slower | 1.6.7 | 1.6.7, CPU 4x slower |
   | --- | --- | --- | --- | --- |
   | 2,000 points | 67 ms | 253 ms | 20 ms | 66 ms |
   | 8,000 points | 766 ms | 2,980 ms | 49 ms | 167 ms |
   | 16,000 points (a minute of shading) | 1,350 ms | 5,748 ms | 14 ms | 54 ms |
   | 40,000 points | 3,764 ms | 15,878 ms | 26 ms | 94 ms |

   Through the API (`Nib.scribble.of`, which Deckhand calls) a small zig-zag at a large scale took 41 s and a
   200,000-point stroke never finished; both now answer at once.
3. **The Replicator cannot be hung by a letter.** A box kept the pointer when the pen slid off it and stored the
   stroke wherever it went; tracing a glyph 10 boxes wide took 0.9 s, 30 boxes 7 s, 100 boxes 43 s or ran out of
   memory, at every change and every load. Strokes are now kept to the box and a box around it as they are drawn,
   saved work and opened files are held to the same range, and the font build is bounded for any input.
4. **Numbers that are not numbers.** A `null` coordinate (what a NaN becomes in JSON) was read as 0, a spike to the
   origin; coordinates near 1e308 and options like `prior: 1e9` left every score NaN and crashed the segmentation;
   the camera took any x and y, so a damaged one opened the board where writing could be neither read nor saved (7
   strokes written, none came back). A coordinate is now a finite number within 1e9 or its point is dropped, options
   that are no numbers take their defaults, the segmentation always has a path, and the camera is held inside what
   can be stored.
5. **Input that is not strokes reads as nothing**, as `test/check.js` already promised: `Nib.recognize(42)`,
   `('abc')`, `({})`, `[[null, null]]` and BigInt points threw.
6. **An unknown `symbols` name on a pad** falls back to the school set with one warning; through the API it is still
   the clear error the suite tests for, now also for `'constructor'`, a number or an object.
7. **Small guards**: `Nib.solve({tree})` with a malformed tree, `pdfFit` with zero sizes, `color` with a non-string,
   `shapeFromDrag` and `scribble.erase` / `.covers` with what is not theirs, a board file that cannot be read.

## The repository

- **Builds do not depend on the platform.** The build scripts opened files with the platform's default encoding and
  line endings: on Windows the non-ASCII in the sources (×, ÷, π) would have been misread and `dist/` written with
  CRLF. They now read and write UTF-8 with LF, and `.gitattributes` keeps LF in every checkout.
- **CI**: read-only permissions, a newer push replaces the run in progress, a weekly run (the data sources and the
  pinned packages still work), a manual trigger, the lint step.
- **Licenses** (`licenses/README.md`): the pages carry DM Sans, DM Serif Display and DM Mono, and the demo page
  carries KaTeX's code; their notices were missing and are added. The recognizer was trained on CROHME, whose terms
  are research and not commercial use: fine for a classroom, not for selling Nib. Nib's own code has no license file;
  that is Croix's decision.
- **KaTeX 0.16.11 to 0.16.47.** Two advisories, neither reachable (the demo page renders the engine's own LaTeX without
  the `trust` option). Its fonts and metrics are byte for byte the same, so the engine's data did not change.

## Found and left

- **After a reload, a full page takes a long time to be read again.** The page stays usable, but answers and the
  tidied views wait until every piece has been read, because the reading is announced once, at the end.

  | On the page | This machine | CPU 4x slower |
  | --- | --- | --- |
  | 20 expressions (219 strokes) | 8.6 s | 31 s |
  | 60 expressions (507 strokes) | 19 s | 69 s |
  | 120 expressions (1,161 strokes) | 47 s | 168 s |

  It is the cost of reading (about 0.02 to 0.05 s a stroke, as the README says), paid again because readings are not
  kept with the board. The fixes are to announce pieces as they are read, what is in view first, or to keep the
  readings with the saved board. Either changes when results arrive, which the suites and hosts depend on, so it is
  its own piece of work.
- **Reading many strokes at once through `Nib.recognize`** takes the same per-stroke time with the page stuck (400
  dashes: 30 s). The pad and `recognizeAsync` do it in slices; a host should use those.
- **Absurd boards open slowly**: 3,000 strokes in one tight cluster are still being read after 45 s; one stroke of 300,000
  points takes 6 s to open. Neither can be made by hand in a lesson.
- **Strokes more than 1e9 units from the origin are dropped when a board is opened.** Nothing written by hand is
  there: the camera could not be panned that far, and now cannot be set that far.
- **A saved board that is not JSON at all** is replaced by the next save. Only something else writing Nib's key can
  cause it.
- **Development tools with advisories**: puppeteer-core's helpers (it only drives Chrome in the tests; nothing of it
  ships; its next major needs the tests rewritten as modules) and KaTeX below 0.18.2 (needs a page already
  compromised).
- **From the first review of the day, still open**: `src/pad.js` is one class of 3,000 lines; there is no engine-only
  build; the training scripts have four generations and no manifest; `docs/HANDOFF.md` mixes reference and history in
  very long lines; the training log shares localStorage with the board.

## Repeating it

`npm test`, `npm run test:browser` and `npm run lint` run everything above that can be kept as a test: the odd-input
cases, the damaged storage, the long strokes, the injected faults, the limits. The mutation sample is not kept as a
suite (each mutant needs a build and a suite run); its method is the table above: change one thing, build, run the
suite that should notice.
