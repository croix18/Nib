# Nib 1.7.0, stage 1: a classifier ten times faster, with the same readings

You are working in `/home/claude/nib` (GitHub croix18/Nib, branch `main`, version 1.6.7, clean tree). Nib reads
handwritten math into LaTeX in the browser: one dependency-free file, `dist/nib.js`, plus pages built from it
(`dist/Board.html` is a classroom whiteboard). Read `docs/HANDOFF.md` selectively first (very long lines): the Files
table, "Pipeline", "Hardening (1.6.7)"; and `README.md`'s closing development notes (`python3 build.py`, `npm run
build`, `npm test`, `npm run test:browser`, `npm run lint`, `npm run data`).

The owner, Croix (a math teacher; the Board runs on a classroom panel and his tablet, from `file://`, offline),
asked: "take on the speed head on. Throw your best at it." The slow thing is reading: after a reload a page of 60
expressions takes 19 s to be read again on this machine (69 s with the CPU slowed 4x), and all of that is the symbol
classifier. This stage makes the classifier fast. A second stage (not yours) will change how the pad schedules reading.

## What I measured (all reproducible; scripts in `/tmp/speed/`)

- `node /tmp/speed/prof.js 40`: a classification (`classifyGroup`) takes 16 ms: the five 3x3 conv layers
  (`convFeatures`) 14.5 ms, the online branch 0.74 ms, the FC layers 0.18 ms, rasterizing 0.04 ms. A cold read costs
  27.6 ms a stroke (about 1.7 classifications a stroke).
- `src/core.js` `conv3` / `conv1` / `fcProbs` accumulate into a `Float32Array` with `out[i] += v * w`: each step is
  computed in double and rounded to float on the store (in effect a fused multiply-add in float32).
- **A hand-written WebAssembly SIMD kernel does the conv stack in 1.13 ms: 13 times faster.** Prototype:
  `/tmp/speed/kern.wat` (1,133 bytes assembled) and `/tmp/speed/bench_kern.js` (assembles it with the `wabt` npm
  package and compares). Its arithmetic is plain float32 multiply then float32 add, in the same order per output
  element as the JS loops, with the sum for an output pixel held in six registers across the input channels.
- **That arithmetic can be written in JS so that the two paths give the same bits**: `out[i] += Math.fround(v * w)`.
  The prototype's features equal that JS's exactly: 0 of 591,360 differ.
- **Changing from the fused arithmetic to plain float32 changes no reading.** I built 1.6.7 with the `Math.fround`
  form (`/tmp/speed/variant/`) and compared every reading of 1,719 expressions (the 700 school expressions, the 239
  board rows, 780 of CROHME's test set) with 1.6.7's: LaTeX, every symbol's label and strokes, the answers after "=",
  and each symbol's top three candidates all identical; the largest difference in a confidence was 2.3e-7. A feature
  itself can move by up to 6e-4 of its size, so this had to be measured, and it must be measured again on your build
  (below).
- Chrome compiles such a module synchronously on the main thread (it is under Chrome's 4 KB limit for synchronous
  compilation) and inside a worker, from a page opened as `file://` with no flags (`/tmp/speed/wtest.js`).

## What to build

1. **One arithmetic, two implementations that agree to the bit.**
   - The classifier's arithmetic becomes: float32 multiply, then float32 add, each output element summed in the order
     the loops in 1.6.7 add its terms (bias first; for a 3x3 conv the taps in order (ky, kx), within a tap the input
     channels in order; zero inputs skipped). State this as the definition in a comment.
   - **The kernel** (`src/kern.wat`, WebAssembly text, SIMD): the five conv layers with their pools, the online
     branch's three 1-D convs with its pooling, and the first FC layer. Start from my prototype; the conv1 and FC
     loops are the same primitive (`$axpys`: out += sum of x[i] * w[i][...] in order of i). The second FC layer and
     the softmax stay in JS (they accumulate in float64, exactly as now). Output channel counts are multiples of 4
     in this model (24, 48, 96, 32, 64, 192); handle the general case correctly anyway, or refuse to use the kernel
     for a model where it is not (fall back to JS).
   - **Assembled at development time, not at build time**: `tools/build_kern.js` assembles `src/kern.wat` with the
     `wabt` npm package (add it to `package.json` devDependencies, pinned exactly, and update `package-lock.json`)
     and writes `src/kern.js`: the bytes as base64 plus the loader. `src/kern.js` is committed. `build.py` stays
     standard-library only: it just takes `kern.js` as one more source (add it to its list in the right place; the
     list is also what `tools/lint.js` reads). `node tools/build_kern.js --check` exits non-zero when the committed
     `src/kern.js` is not what the WAT assembles to; add `npm run kern` and that check to CI's node job
     (`.github/workflows/test.yml`, one step beside the lint step).
   - The assembled module must stay under 4,096 bytes (Chrome refuses to compile a larger one synchronously on the
     main thread). `tools/build_kern.js` fails above that, and a test checks it.
   - **The loader**: on first use, try `new WebAssembly.Instance(new WebAssembly.Module(bytes))`; any failure (no
     WebAssembly, no SIMD, a Content-Security-Policy that forbids it, anything thrown) means the JS path, quietly
     (one `console.info`, not a warning). The weights are copied into the module's memory once. Declare the memory
     in the module, large enough for the weights and the activations, and never grow it.
   - `Nib.kernel` (read-only: `'simd'` or `'js'`, decided on first use; reading it decides it). For tests:
     `Nib._internals.kernelUse('js' | 'simd' | 'auto')`.
   - **The JS path** is the reference and the fallback: `convFeatures`, `onlineBranch`, `fcProbs` written in the
     defined arithmetic, bit-identical to the kernel. It must not be slower than 1.6.7's (14.5 ms for the conv stack
     here); my naive `Math.fround` version measured 18 ms, so find the form V8 compiles to float32 operations (try
     `out[i] = Math.fround(out[i] + Math.fround(v * w))`, and the kernel's loop order: tap, pixel, channel, output),
     and measure. It runs where WebAssembly is not allowed, so it matters.
2. **Then profile a cold read again** and take what is next, only where the result is bit-identical: the online
